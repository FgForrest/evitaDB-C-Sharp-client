# Divergences from the Java driver

The Java implementation is this repo's source of truth (see `CLAUDE.md`). This file records places where the
C# driver's *behaviour* differs from its Java counterpart — both deliberate adaptations and defects found in
the porting.

Each entry names the Java class and line so the comparison can be re-run against a checkout of the matching
tag. Verified against **evitaDB `v2026.2.4`** (`/Users/tomas/www/evita/evitaDB`), the tag
`AdvertisedClientVersion` targets.

Deliberate deviations documented elsewhere are listed at the end rather than duplicated.

---

## 1. `ModelSchemaAnalyzer` and generated primary keys — **fixed**, one deliberate deviation remains

**C#:** `EvitaDB.Client/Models/Typed/ModelSchemaAnalyzer.cs` (`ApplyPrimaryKeyGeneration`)
**Java:** `evita_api/.../requestResponse/schema/ClassSchemaAnalyzer.java:1495-1512` (`definePrimaryKey`)

Java's `definePrimaryKey` has three properties: it emits **both directions** (`autoGenerate = false` actively
calls `withoutGeneratedPrimaryKey()`), it is **guarded on the builder's current state** so re-analysing a
schema that already agrees emits nothing, and it has **one source of truth** (`@PrimaryKey.autoGenerate()`;
Java's `@Entity` has no primary-key member).

The first C# port had none of them: it OR'd `[EvitaEntity(GeneratedPrimaryKey = …)]` with the `[PrimaryKey]`
member (whose `AutoGenerate` defaults to `true`, as in Java), never called `WithoutGeneratedPrimaryKey()`, and
never read the builder's state. `false` was therefore unrepresentable, and a collection that had once acquired
the flag could not be talked out of it — which turned a caller mistake (a bare `[PrimaryKey]` on a contract
that supplies its own keys) into a permanent `Entity of type X is expected to have primary key automatically
generated by Evita!` refusal. The mistake itself would fail identically in Java; what differed was that Java
lets the next definition pass correct it and C# did not.

**Now:** the analyzer mirrors Java. A member annotated with `[PrimaryKey]` is the only source when present and
its `AutoGenerate` is applied in both directions; a mutation is emitted only when the schema's current value
differs. Covered by `TypedModelTest` (`ShouldTurnGeneratedPrimaryKeysOffWhenTheMemberSaysCallerSupplied`,
`ShouldNotEmitAPrimaryKeyMutationWhenTheSchemaAlreadyAgrees` and neighbours).

**Remaining deliberate deviation.** C# keeps the entity-level `EvitaEntityAttribute.GeneratedPrimaryKey` flag
Java does not have, as a *fallback* for contracts without an annotated key member: `true` turns generation on,
`false` (the default) leaves the schema alone. A primary key that is only inferred from its name (`int Id`)
expresses no schema intent — consistent with the analyzer's rule that inferred members read data without
defining it — so such a contract leaves the decision to the server's `ADAPT_PRIMARY_KEY_GENERATION` evolution
rule. Java has no inferred primary keys at all, so there is nothing to compare there.

## Deliberate deviations recorded elsewhere

Not defects — design decisions, documented where they are relevant:

| Deviation | Where it is documented |
|---|---|
| Proto message `DataItemMap` renamed `GrpcDataItemMap` (wire-compatible; C# name-collision fix) | `CLAUDE.md` hard rule 5 |
| Async core with a sync facade (`XxxAsync` implementation, sync wrappers) instead of Java's `CompletionStage` | `documentation/async-api.md` |
| Streaming APIs as `IAsyncEnumerable` (`MoveNextTranslated`) rather than Java's stream observers | `documentation/async-api.md` |
| Deprecated-wire-field fallback-read / dual-write, and scope projection onto the live scope | `documentation/wire-compatibility.md`, `CLAUDE.md` hard rule 2 |
| Records, default interface methods and other idiomatic-C# reshaping of `evita_api` contracts | `documentation/architecture.md` |
| The typed-model layer (`Models/Typed`) as a whole — the annotation set is modelled on Java's but is not a 1:1 port | `documentation/typed-models.md` |

The last row is why entry 1 is worth recording rather than fixing silently: the typed layer is close enough to
Java's `ClassSchemaAnalyzer` that its omissions read as ports, and far enough that no one thinks to diff them.

## Adding to this file

Record a behavioural divergence, not a stylistic one. An entry earns its place when a caller who read the Java
documentation would be wrong about what the C# driver does. Name the Java class and line, state what Java does
and what C# does, and say whether it is deliberate. Verified against a tag, so the citation stays checkable —
see `documentation/upgrading-evitadb.md#known-porting-pitfalls` for the recurring families.
